# Minimap: design notes

What an agent working on this plugin must know. The user-facing description is `README.md`; this is the why. Everything here was checked against bb-app 0.49 and is undocumented BB behaviour unless said otherwise.

## Rules that bite

- **No Tailwind utility words anywhere in the folder.** `bb plugin build` turns a bare Tailwind class word in code, comments, labels, tests, README or this file (the names of CSS display, position, overflow, animation and effect values are the usual ones) into a page-wide `:where([data-bb-plugin="minimap"], …) .word` rule that is matched on every style recalc. Such words are built from two strings (`FLOAT`, `ROW`, `ABS`, `REL`, `SIZED` in `src/Panel.tsx`; `--minimap-pos` in `src/strip.ts`; the animation and softening words in `src/tip.ts`; `inBackground` in `src/tab.ts` for the tab's background flag) or reworded; never list them in a doc. After every build run `grep -c ':where(\[data-bb-plugin=' dist/app.css`: it must print 0, and when it does not, the regex `\) \.([a-z0-9\\:\[\]-]+),:where` over the file names the words.
- **Headless pages read the user's real settings.** `GET /api/v1/plugins/minimap/settings` returns them (they had `wheelSmooth` and `clickSmooth` off at times). Force values with `page.setRequestInterception(true)` and answer that request; never write the user's settings.
- **Don't open `src/shared.ts` for writing with a one-expression read-and-write** (`open(p,'w').write(open(p).read()…)` truncated a file once).
- A thread action, `bb plugin reload minimap` after each build; headless runs `bb browser-automation open --backend local --headless`, screenshots as JPEG, one script call under 120s.

## Shape

- `app.tsx` is an app overlay: `Overlay` mounts one `<Minimap>` per thread on the page and the one floating `<Panel>`. BB hands a plugin only the focused thread (`useBbContext`), so `paneThreads` reads each timeline's thread off the page (the prefix of its first `[data-timeline-row-id]`) and `usePaneThreads` looks again every `PANE_SCAN_MS` (1s, stopped while the tab is in the background, one look when it returns; no observer on the rows). A split workspace therefore gets a strip on every pane, and a pane that closes or switches thread loses or swaps its own. A strip, its note, painter and watcher are per thread; the panel and settings are one. A strip waits for the focused thread to settle (`useSettled`: two frames, then idle, 1.5s at most), because opening a thread is BB's busiest moment.
- `src/Minimap.tsx` renders nothing: it creates the strip (`createStrip`) and the timeline watcher (`watchTimeline`) in one effect and passes rows from one to the other.
- `src/strip.ts` is the controller outside React: puts a `.minimap` host into the scroller's parent (a canvas, the slider `div.minimap-view`, colour probes `.minimap-ink[data-kind]`), runs a **pass** (measure the mounted rows, build the layout, draw, place the slider, `tip.refresh()`) at most every 250ms from a ResizeObserver on the scroller and its frame, 140ms after scrolling stops, and on new rows. Scrolling itself only moves the slider (`translate` in one rAF). `applyOptions` copies the options onto the host as `data-*` and `--minimap-*` properties; `placeToc` moves or hides BB's thread-index button.
- `src/painter.ts` sizes the canvas and paints the boxes it is handed; it slides a change for 260ms (new rectangles fade in, gone ones out; not on a change of size, the first draw, reduced motion or over `TWEEN_MAX` 1500 boxes) and **skips a draw whose boxes and colours equal what is on the canvas** (a pass that only changed text, which on a live thread is about one per second).
- `src/boxes.ts` (pure): `boxesOf`, `boxAt`, `paintList`. User messages and errors are painted over the rest and never thinner than 2 device pixels; past one box per two device rows each layer keeps one box per device row, so a 12,000-row thread paints about 2,800 rectangles (9.3ms a repaint).
- `src/steering.ts`: click, drag, wheel and the follow of a clicked row (see Scrolling).
- `src/tip.ts` + `src/window.ts` + `src/icons.ts`: the hover note.
- `src/model.ts` (pure): the layout (below), `glideStep`, `shadeAlpha`, `scrollForClick`/`scrollForDrag`, row-kind helpers. `src/rows.ts`: an `Item` per row (estimated height, kind, note text), `applyDelta`. `src/timeline.ts`: the watcher.
- `src/shared.ts` is every setting once (`SETTINGS`), with no imports so the page bundle does not pull in zod. `server.ts` defines the settings from it (dropping `min`, `max`, `short`, `hint`, `unit`, which the settings API rejects), the RPC inputs (`set_setting`, `set_number`, `set_color`, `reset`) and the number clamps. A new option is one `SETTINGS` entry (`label`/`description` for the API, `short`/`hint`/`unit` for the panel), one line in `Options`/`stripOptions` (`src/options.ts`), and where it is used; `src/shared.test.ts` checks the list, that every setting has words, and the defaults. Percent settings are 0 to 100 as saved and in the panel and 0 to 1 in the options (`SHARE_KEYS`).

## Reading the thread

- `src/timeline.ts` reads `sdk.threads.timeline` with `deferContent: "true"` (no estimate reads a tool row's content) and refreshes as deltas: the newest page is held with its `tag`, a refresh asks `afterTag`, and `applyDelta` (`src/rows.ts`: `upsertRows` in place, `rowOrder` as `[from, to)` stretches of the held page plus new ids) rebuilds the page. A refresh is about 2KB against about 170KB for BB's own reads. A delta that does not fit, `history-rewritten`/`-compacted`, or 60s since the last full read (`FULL_EVERY_MS`) reads in full. A delta also carries `fields.timelinePage.olderRowUpdates`. Measured on a live thread: 11 non-empty deltas all rebuilt exactly what a full read returned.
- Nothing is read while the strip is not shown or the tab is in the background (`setActive` from `Strip.onShown` and `visibilitychange`; signals then only mark the rows stale and becoming active reads once). The module uses the global `setTimeout`/`Date` so `src/timeline.test.ts` runs it under `mock.timers`.
- Older pages: only the newest page by default. With `loadHistory` older pages are read one at a time 250ms apart (up to `MAX_ROWS` 12000); otherwise only while the strip reports `onNeed` (`lead` above `LEAD_SLACK` 120px: BB has loaded older rows than are held). Merged by id.
- `src/remember.ts` keeps each thread's measured row sizes and column width for the last 6 threads, so returning settles at once (dropped if the column moved more than 2px). Rows and the delta tag are not kept.

## The layout (why the strip does not just read the DOM)

BB virtualises the timeline at 20 or more top-level rows: unmounted ranges are `[data-timeline-window-spacer]` placeholders with estimated heights, and `scrollHeight` shifts as rows measure (it doubled over a long thread while scrolling, so a map fitted to the spacers drifted for seconds). So `buildLayout` (`src/model.ts`) lays every item in **the strip's own pixels**: a measured height (rows on screen now, or cached by row id; cleared when the column width changes) or its estimate times a per-kind calibration learned from measured rows (needs 3, clamped 0.4 to 3). `inScrollerPixels` then puts the finished layout into the scroller's pixels (rows on screen keep their real places, the stretches between are scaled to what the scroller holds), so the strip is a scrollbar track with blocks on it: its total is `scrollHeight`, the slider is a linear share of `scrollTop` exactly where the native thumb is, and `ownOf`/`bbOf` are the identity on it. `Layout.bbs`/`owns` are matching points (rows on screen plus both ends) that convert a scroll position to a spot on the strip and back. The strip moves a little when BB replaces estimates, as the thumb does; the 260ms slide smooths it.

- `lead` is the scroller height of older history the data has no rows for (`hasOlder`): exact whenever the first item is on screen, a guess (`estimateLead`) before; drawn blank until `onNeed` has fetched the pages.
- A finished turn's work is one `<turn>:turn:0` "Worked for" row, so its `work` rows are estimated at 0px. While a turn works BB folds tool calls into lines (ids `<turn>:work-summary:<data id>`, each standing for several data rows, direct children of the items box): `foldedHeights` gives the first data row of a line the line's height and the others 0, and `dataIdOf` maps a DOM id to a data id.
- A user message is estimated at most `USER_MAX_H` 380px (BB cuts a long one short; a 3,900-character first prompt drew a giant rectangle). User rectangles are right-aligned and as wide as the bubble (`bubbleShare` reads `[data-message-column]`'s first child).
- The slider is the viewport height times the scale. The scale is always strip height over content height, so a short thread spans the strip.
- Colours are the `.minimap-ink[data-kind]` probes read with `getComputedStyle` (a canvas takes no `var()` or `light-dark()`), re-read when `<html>` attributes or the colour scheme change; a colour set on a Blocks row is written on the element itself on its probe. A canvas cannot read `oklab(…)` back, so the panel's `themeColor` reads a pixel.

## Placement

- The strip hugs the scroller's right edge like a scrollbar. With `hideScrollbar` off it is also inset at top and bottom by the larger of `BAR_INSET` 11px and the scrollbar's width (the native track's ends), so the slider tracks the thumb. `keepScrollbar` sets an on the element itself `scrollbar-color` because BB's `.thread-scrollbar` is transparent until `data-scrollbar-scrolling`.
- BB's `[data-thread-toc]` is moved left of the strip (`data-minimap-toc="left"`, `--minimap-shift`) or out of view (`hideToc`, the default), and restored on detach.
- The strip is removed from view below a gap of `MIN_GAP` 8px between the column and the strip unless `keepNarrow` (the default): then it stays at `narrowWidth` over the column's edge. `hideWhenFits` hides it while `scrollHeight <= clientHeight + 1`.
- `z-index: 26`: above BB's pane divider (z-25, a transparent handle 12px wide that reaches 6px over a pane's edge and otherwise took the left pane's clicks). Menus are at 50, toasts 49, BB's phone drawer 45.
- Phone: the panel is a bottom sheet up to 640px; the strip itself has no phone rules beyond the narrow width.

## Scrolling (`src/steering.ts`)

- Every write to `scrollTop` first dispatches a synthetic `wheel` on the scroller: BB 0.48+'s scroll keeper writes an unexplained scroll back to the bottom while attached there, and a wheel counts as the reader's input. A slow frame can outlast the keeper's window anyway: the follow rewrites the aimed place when the row is not on screen, and the glide does not follow a snap to the bottom (`snapped`). This made the first click in a split pane do nothing.
- Click: `clickSmooth` (default on) aims the same glide as the wheel (`aim`), and `steer` waits for it before following the row under the click each frame (BB swaps estimates for measurements while rows mount). The browser's `scrollTo({behavior:"smooth"})` was used first and is cut short whenever BB changes row heights during it (a click at 15% ended with the slider at 79%); with the glide, clicks at 15, 40 and 70% end at 17, 41 and 70%. A press off the slider is a drag only after `DRAG_PX` 4px of travel (a 1px wobble used to cancel the glide into a jump).
- Drag: pointer capture, the slider keeps its place under the pointer, `scrollForDrag`.
- Wheel: forwarded at `wheelSpeed` percent (default 300, 25 to 1000). With `wheelSmooth` the glide is our own: steps move `wheelTarget`; a rAF loop moves a float `wheelPos` by `glideStep` (share `1 - exp(-dt/GLIDE_MS)`, 90ms, landing exactly once within half a pixel, because Chrome rounds `scrollTop` and a test against the scroller's own value never arrived, which kept the loop and its synthetic wheel events going forever) and writes it. It carries position and target along when something else moves the scroller (`wheelSeen`), clamps the target each frame, and ends on any trusted wheel, touch, pointer or key input outside the strip (`GLIDE_STOPS`, capture listeners on `window` only while a glide runs). Reduced motion jumps.

## The hover note (`src/tip.ts`, `src/window.ts`)

- One `div.minimap-tip` on `document.body` (not in the thread's subtree: a text change anywhere inside it cost about 50ms of layout a time in a trace, 23 slow frames in a 136-frame sweep; the same change on `body` cost nothing) with its own position set from the host's rect each frame, plus one `div.minimap-hot` in the host (an inset 1px line in the rectangle's own ink). Both are reused for every row and moved from one rAF-read `pointermove`; nothing runs unless the pointer is on the strip. Hidden on leave and when the strip goes, not on a press or drag.
- The note sits at the pointer's height (a `translate`, no animation) with an arrow at the pointer. `nearest` picks the drawn rectangle under the pointer or the next, whichever is closer; a pointer in a gap keeps the note. A new row is taken at most every `hoverDelay` ms (66).
- The note is a window onto a lazily built list: `2 * hoverContext + 1` slots of `hoverLines` lines (`LINE_H` 17 + `PAD` 5 either side), the pointer's row in the middle and bright. `windowStart` (`src/window.ts`) moves the window inward at either end of the thread; `planLines` says which lines a glide builds, refreshes and drops (those more than `FAR` 24 rows from the move); `isJump` says when to clear and set the window at once (the first show, more than `FAR` rows, animation off). These are pure and tested in `src/window.test.ts`, including a sweep of 24-row hops that must never leave the window empty.
- Rows are tracked by id among the rows the strip draws (`drawnRows`, `firstAtOrAfter`): a kind switched off in Blocks takes no place, and a shown row that moves in the layout (older history loaded above it, a turn folding) makes the window start over. A pass calls `tip.refresh()`, the strip hiding calls `tip.hide()`, built lines are brought up to date in place (`fill`: streaming text, a turn's step count; on a same-row refresh every line of the window).
- A change glides the list with one CSS animation on its `translate` (`hoverAnimate`, `hoverSlideMs` 420); a glide over more than one row also softens the list (a Web Animation on its softening, 0 to `hoverBlur` px, at its peak after `SOFT_ROWS` 8 rows, going down along the glide's curve). Lines show a small icon in their rectangle's colour (`src/icons.ts`, drawn with `createElementNS`, set on the element itself because BB's base style makes an svg a box) and the start of the row's text (`Item.tip`; `Item.more` holds the first lines for a note of several; a work row shows BB's own `presentation.title`, a turn its step count).

## The shade

`edgeShadow` and its options set `data-cast="strip"|"right"`, `data-layer="over"`, `data-tone="theme"`, `data-dark` and `--minimap-shade`, `--minimap-w`, `--minimap-reach` on the host. The alpha is `shadeAlpha(edgeStrength/100)` (strength to the 0.434, so the slider still does something at its end and the default 44 gives 0.7): black at that alpha on a dark theme, 0.35 of it on a light one (nothing with `edgeDarkOnly`, the default), Theme colour mixing `--background` at 125% of it. The host is clipped to its height by `clip-path: inset(0 0 0 -reach)`. From the strip's edge it is a `box-shade` of the host, or with the layer over a softening from a zero-width `::before` (softening 3/4 of the reach, spread 1/4, so it ends exactly at the reach; half the reach as spread ended in a hard line); from the right edge a `::before` gradient across the strip and `reach` beyond it. All sit below the slider.

## The panel and BB's settings page (`src/Panel.tsx`)

- A 760px floating panel opened by the thread action (`src/ThreadMenu.ts`, `setPanelOpen` in `src/panelState.ts`), dragged by its title bar (pointer capture, clamped with 48px on screen, not remembered), Esc or × closes. Six tabs (Behaviour, Strip, Scrolling, Blocks, Slider, Note); Strip and Note hold groups as a second row of tabs (`GROUPS`: Strip has Size, Fade, Scrollbar, Shade; Note has Preview, Glide). Up to 640px wide it is a bottom sheet (80dvh high, tabs three to a row, `!important` over the drag position).
- Rows read their words from `SETTINGS` (`shortOf`, `hintOf`, `unitOf`), so wording is edited in one place; a dependent setting is set in by `indent`.
- `Content` is shared with the Minimap section of BB's settings page (`SettingsPage`, `app.slots.settingsSection`, in the page's flow with `data-page`). A rule in `src/styles.css` hides the plain list BB generates from the setting definitions inside `[data-testid="plugin-detail-minimap"]`; both test ids are BB's, so check that page after a BB upgrade.
- Tabs and segments follow their roles (`rove`: arrows, Home, End; only the selected one is a tab stop; the body is a `tabpanel`; the floating panel focuses the selected tab on open).
- The SDK has no switch or slider component, so they are plain elements. Sliders and colours preview on the strip while dragged (`src/preview.ts`, a store `useOptions` overlays on the saved values; `setOptions` asks for an urgent pass) and are written once on the control's native `change`, when its tab or the panel closes, or 600ms after the last step (`usePreviewed`); the preview is dropped when the saved value equals it or the write fails. "Reset all" calls the `reset` RPC (every default in one `experimental_set`) and asks twice.

## Standing timers

- The strip's 1s look for a rebuilt scroller and the pane scan in `app.tsx` do not run while the tab is in the background and look once when it returns (`inBackground`, `visibilitychange`). The timeline watcher reads nothing while inactive. The note's throttle and the strip's pass timers are one-shot and started by input.
- Idle cost seen headless: on a quiet thread 3 passes and 0 repaints in 15s; on a live one a pass about each second with the repaint skipped when nothing moved.

## Testing

`pnpm test` in `bb-plugin-minimap/` (`node --test src/*.test.ts`, 87 tests): the layout and click/drag maths, `glideStep`, `shadeAlpha`, rows and deltas, the watcher under mock timers, boxes and paint list, the note's window rules, preview and remember stores, `SETTINGS`. Not covered by tests: the DOM parts of `strip.ts`, `tip.ts` and `steering.ts`, and `Panel.tsx`; those are checked headless. Headless frames are slow (200ms), which is what exposed the keeper snap.

## Known gaps

Three or more panes and a real phone are untested. Review items left on purpose: the note naming an unpainted row on a very dense strip, small touch targets in the panel, the panel sitting under BB's phone drawer (z-index 40 against 45), `Item.more` memory at 12,000 rows with `loadHistory` on (about 2 to 4MB, estimated).
