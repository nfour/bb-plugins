# BBPlugins

A pnpm workspace of BB plugins. One folder per plugin, `bb-plugin-<id>/`, each a normal BB plugin package (`package.json` carries the `bb` manifest). Use the `bb-plugin-authoring` skill for the Plugin SDK contract.

## Code here, run it from bb

Write all plugin code in this repo. Never edit a plugin inside `~/.bb/plugins/` — that directory holds BB's runtime state, not source. Link a plugin by path so bb loads this checkout in place:

```sh
bb plugin install ./bb-plugin-<id> --yes   # once per plugin
bb plugin dev ./bb-plugin-<id>             # rebuild + reload on every save
```

## Workspace

- Install with `pnpm install` at the root, never `npm install` in a plugin.
- `pnpm check` typechecks every plugin; `pnpm build` runs `bb plugin build` in each; `pnpm --filter <pkg> test` runs a plugin's `node --test` checks (pinned-turns, diff-plus, lexicon, performance, guest-view, minimap).
- `bb plugin types ./bb-plugin-<id>` repins the SDK when bb upgrades.
- Releases are tags `<id>/vX.Y.Z`; `.bb/plugins.json` indexes the plugins for git installs. Each release bumps `package.json`'s version and adds an entry at the top of the plugin's `CHANGELOG.md` (what a user notices, not the code), in the same commit as the change.
- Styling: no Tailwind utility classes. `bb plugin build` scopes every utility it finds anywhere in the folder (code, comments, README) as `:where([data-bb-plugin="<id>"], …) .flex`, and BB's own elements carry the same class names, so each rule is matched page-wide on every style recalc (most of a thread switch's style time with many plugins). Write prefixed classes (`pinned-*`, `chat-dock-*`, `diff-plus-*`) in `src/styles.css`, imported from `app.tsx`; check `dist/app.css` for `:where([data-bb-plugin=` after a build.

## Plugins

- `bb-plugin-pinned-turns` — pins the message you are reading under and the latest reply to the top of the timeline. `src/model.ts` holds the pure rules (`bandAt` is tested against the simple `bandContent`); `src/timeline.ts` holds the hooks that read the timeline and outline through the SDK, and `src/watch.ts` the watcher behind them (no React import, so `src/watch.test.ts` runs it under `node --test` with `mock.timers` and a fake SDK): the newest page is kept with its `tag`, and a refresh asks `afterTag` with `deferContent: "true"` and `applyDelta` (`src/rows.ts`) rebuilds the page (a few KB against ~80KB; a delta that does not fit, `history-rewritten`/`-compacted` and 60s since the last full read read it in full); nothing is read while the bar is not on the page or the tab is hidden (`active`: signals only mark the rows stale, becoming active reads once, and the outline for the counter follows the same rule). The bar reads only a message's text and a row's kind, status, `systemKind` and `operationKind`, none of which `deferContent` drops. Jumps steer by the row's live position each frame rather than one `scrollTo` (BB re-measures rows mid-scroll), and never touch the URL or history. Its options are a `choices` submenu of a thread action (`src/ThreadMenu.ts`; BB 0.48 retired the custom header-button slot, and header actions cannot hold choices), written through the backend's `set_setting` RPC. BB 0.48's scroll keeper writes an unexplained scroll back to the bottom while attached there, so each jump frame first dispatches a `wheel` event on the scroller to count as reader input.
- `bb-plugin-chat-dock` — moves BB's live composer shell (`[data-app-composer]`) into the right panel with `moveInto` (`src/dom.ts`), which leaves a marker and puts it back, so the draft survives. One page-wide MutationObserver docks it before a paint. The composer button only toggles `enabled` (a document capture-phase `pointerdown` guard keeps BB's composer from expanding on its click); the options are a `choices` submenu of a thread action (`src/ThreadMenu.ts`), like Pinned Turns'. Headless checks need `page.mouse.click` on the button. Docking goes through `dockInto` (`src/dom.ts`): in the split panel it is `moveInto`; in the phone drawer, which is outside React's root, the shell goes into an overlay instead (`src/overlay.ts`: a layer appended to `#root`, sized to the drawer's content box and z-index plus one by a `ResizeObserver` on the drawer, with the frame at its bottom; the host left in the drawer keeps the frame's height and `aria-owns` it), so `holdsShell`/`heldShell` look in the overlay, and the strip finds a host the tab parked in the drawer there too. No script runs on scroll, tap or drag. The narrow side panel keeps the composer footer shown with `all: revert-layer` on BB's fade (strip and tab hosts only, not the overlay); don't override `--follow-up-composer-container-compact` instead, BB's composer also reads it for its one-line layout. Changing `locked` to test the Chat tab writes the user's setting: rewrite `GET /api/v1/plugins/chat-dock/settings` in a headless page instead.
- `bb-plugin-performance` — a nav-panel tab (`app.slots.navPanel`, route `/plugins/performance/performance`) that measures how far BB is from feeling native in the user's real sessions, and which plugin is behind a slowdown. Not released yet. The page side is `src/collector.ts`, a content-script singleton that attaches only while `enabled`: PerformanceObservers for `long-animation-frame` (scripts attributed to a plugin by `sourceURL`, matched to each plugin's bundle URL from `GET /api/v1/plugins`; anything else is BB core) and `event` (typing and click latency), a rAF frame sampler that runs only within 400ms of a key, wheel, scroll or pointerdown, the Navigation API `navigate` event plus a MutationObserver that settles after 100ms of quiet (capped 2s) for thread switches and page changes, an attribute observer on `data-panel-size` for panel opens, a 30s timer for heap samples, and a count of each plugin's page-wide `) .word` rules from `document.styleSheets`. Frames in the first 10s of a fresh load are start-up, never idle. Windows are histograms (`EDGES` in `src/model.ts`), flushed once a minute and on `pagehide` through the backend's `ingest` RPC, one flush at a time. `src/model.ts` is the pure core (targets, histograms, `measures`, `pluginRows`, `ownerOf`, `driverAt`, `heapSlope`), tested with `src/jsonl.ts` and `src/proc.ts`. `server.ts` appends lines to `~/.bb/plugins/performance/metrics/YYYY-MM-DD.jsonl` (14 days, 5MB per file; no ids, titles or text are written, routes have ids stripped), keeps the last 400 lines for the dashboard's `snapshot` RPC, serves `recent_threads` (ids only, for the benchmark), and samples the server once a minute (event loop delay, CPU, RSS, `bb.host` workers from `/proc`, handler call deltas per plugin from the page-reported `handlerStats`); `bb performance summary|files` reads the file. Plugin back-ends run inside BB's server process (the log's `pid` equals the server's), so only `bb.host` workers have their own CPU and memory; `handlerStats.maxMs` is lifetime wall time including awaits, so it is written but never shown. React renders of a plugin count as BB core in Long Animation Frames. The charts are plain SVG in `src/charts.tsx` (no library; `series` and `shares` in `src/model.ts` bucket the window lines): bars, trends and the plot area stretch with `preserveAspectRatio="none"` and non-scaling strokes, but any dot is an HTML box over the SVG (`.perf-pt`), because stretched circles turn oval. The plugin rows are an accordion (`PluginDetail` in `src/Panel.tsx`); a probe time includes restyling the plugin's own elements on screen, so the elements are shown beside it. Forced layout is recorded per call site in `window.sites` (`owner · file (BB core only) function@position`, top 12 per window by `topSites`); in BB's bundle the top sites are React's scheduler (`E` in boot-vendor) and its discrete-event dispatch, so the cost is React render and layout effects, not one function. Slow frames that two pages sharing a process both report (same ms, within 50ms) are listed once. The nav icon's badge (`experimental_useBadge`) is the worst gap as a multiple of its target, from what this page has already sent. Options (`enabled`, `writeFile`, `sampleServer`) are a `choices` submenu of a thread action (`src/ThreadMenu.ts`) written through `set_setting`. The panel gets no scroller from BB, so `.perf-scroll` (`height: 100%`, `overflow-y: auto`) is its own; headless wheel events do not scroll, use PageDown. Use BB's own icon names (`TimeSchedule`, `ArrowReloadHorizontal`): an unknown name renders a fallback bolt. Utility words are avoided in the whole folder (the table element and the page's hidden property are built from two strings in `src/Panel.tsx` and `src/page.ts`); check `dist/app.css` for `:where([data-bb-plugin=` after a build. A headless browser draws on the CPU, so its frame numbers are far worse than a real screen's; `bb browser-automation` screenshots must be JPEG (a PNG request stops the session).
- `bb-plugin-minimap` — a strip over the right gutter of each thread's timeline that stands in for the scrollbar. `app.tsx` mounts `Minimap` (renders nothing) per thread once the page is idle; `src/strip.ts` is a controller outside React that puts a `.minimap` host into the scroller's parent, with one `<canvas>` and a slider `div`. Rows come from `src/timeline.ts` (reads with `deferContent`, since no estimate reads a tool row's content, and refreshes as deltas: the newest page is held with its `tag`, a refresh asks `afterTag` and `applyDelta` (`src/rows.ts`: `upsertRows` put in place, `rowOrder` = `[from, to)` stretches of the held page and new ids) rebuilds the page, so a refresh is about 2KB instead of the whole page; a delta that does not fit, a history rewrite or 60s since the last full read (`FULL_EVERY_MS`) is read in full; a delta also carries `fields.timelinePage.olderRowUpdates`. Measured against a live thread: 11 non-empty deltas all rebuilt exactly the page a full read returned. Nothing is read while the strip is not shown or the tab is hidden (`setActive`, from `Strip.onShown` and `visibilitychange`; signals only mark the rows stale, and becoming active reads once if any came). Uses the global `setTimeout`/`Date` so `src/timeline.test.ts` runs it under `node --test` with `mock.timers`. Newest page; older pages one at a time 250ms apart with the `loadHistory` option, off by default because a long thread takes long and costs a lot, and otherwise only while the strip reports `onNeed` (`lead` above `LEAD_SLACK` 120px: BB has loaded older rows than are held, so `setNeed` fetches until the strip has caught up; measured on a 576-row thread: 64 → 120 → 160 rows, `lead` 0, own total within 1% of `scrollHeight`); merged by id as Pinned Turns does; `src/rows.ts` makes an `Item` per row with an estimated height and kind, memoised by row id) and the layout from `src/model.ts` (pure, tested): the strip has its own pixels, not the scroller's: every item is laid at its measured height (rows on screen now, or cached by row id, cleared when the column width changes) or at its estimate times a per-kind calibration from the measured rows (needs 3, clamped 0.4 to 3), so the map holds still while BB swaps its spacer estimates for measurements (BB's `scrollHeight` doubled as a long thread was scrolled through, which made the old map, fitted to the spacers, drift for seconds). The finished layout is then put into the scroller's pixels by `inScrollerPixels` (rows on screen keep their real places, the stretches between them are scaled to what the scroller holds), so the strip is a scrollbar track with blocks on it: its total is `scrollHeight`, the slider is a linear share of `scrollTop` exactly where the native thumb is, and `ownOf`/`bbOf` are the identity on it (the strip does move a little when BB replaces its estimates, as the thumb does; the 260ms tween smooths it). Before this, the strip stayed in its own pixels and the slider drifted up to ~4% from the thumb between the ends. `Layout.bbs`/`owns` are matching points (the rows on screen, plus both ends) that `ownOf`/`bbOf` interpolate to turn a scroll position into a spot on the strip and back (slider, click, drag). `lead` is the scroller height of older history the data has no rows for (`hasOlder`): exact whenever the first item is on screen, a guess from `estimateLead` before, drawn blank until `onNeed` has fetched the pages (BB loads older pages itself near the top). The slider is the viewport's height times the scale (`clientHeight * scale`), not a mapped span, so it matches the scrollbar thumb to within a few pixels once the estimates settle. BB folds a finished turn's work into one `<turn>:turn:0` "Worked for" row, so a `work` row of a finished turn is estimated at 0px; a DOM id `…:work-summary:<id>` is looked up by `dataIdOf`. While a turn works BB folds its tool calls into lines ("Explored 3 files, ran 2 commands") that are direct `[data-timeline-row-id]` children with ids `<turn>:work-summary:<data id>`, each standing for several data rows (the rows of an expanded line are nested inside it, not direct children, so its one measured height covers them): `foldedHeights` (`src/model.ts`) gives the first data row of a line the line's height and the others 0 (to the next row on screen, or the end of the run of work when that is in sight, else only the first), written to the cache each pass, instead of 26px a tool call; the per-kind calibration then also learns the work ratio from them. Expanding a line changes the frame's height, which the ResizeObserver turns into a pass. A user message is estimated at most `USER_MAX_H` 380px (BB cuts a long one short: a 3,900-character message is 379px, and the first prompt of a thread is often this long, so an uncapped estimate drew a giant block at the strip's top). User rectangles are right-aligned and as wide as the bubble (`bubbleShare` reads `[data-message-column]`'s first child). Scrolling only moves the slider (`translate` in one rAF); the canvas is redrawn by a pass at most every 250ms, requested by a ResizeObserver on the scroller and its frame, 140ms after a scroll stops, and on a new `Rows`.
