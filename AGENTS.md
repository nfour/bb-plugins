# BBPlugins

A pnpm workspace of BB plugins. One folder per plugin, `bb-plugin-<id>/`, each a normal BB plugin package (`package.json` carries the `bb` manifest). Use the `bb-plugin-authoring` skill for the Plugin SDK contract.

## Code here, run it from bb

Write all plugin code in this repo. Never edit a plugin inside `~/.bb/plugins/` — that directory holds BB's runtime state, not source. Link a plugin by path so bb loads this checkout in place:

```sh
bb plugin install ./bb-plugin-<id> --yes   # once per plugin
bb plugin dev ./bb-plugin-<id>             # rebuild + reload on every save
```

## Workspace

- Install with `pnpm install` at the root, never `npm install` in a plugin.
- `pnpm check` typechecks every plugin; `pnpm build` runs `bb plugin build` in each; `pnpm --filter <pkg> test` runs a plugin's `node --test` checks (pinned-turns, stay-at-bottom, diff-plus, lexicon, guest-view).
- `bb plugin types ./bb-plugin-<id>` repins the SDK when bb upgrades.
- Releases are tags `<id>/vX.Y.Z`; `.bb/plugins.json` indexes the plugins for git installs. Stay at Bottom is not released. Each release bumps `package.json`'s version and adds an entry at the top of the plugin's `CHANGELOG.md` (what a user notices, not the code), in the same commit as the change.
- Styling: no Tailwind utility classes. `bb plugin build` scopes every utility it finds anywhere in the folder (code, comments, README) as `:where([data-bb-plugin="<id>"], …) .flex`, and BB's own elements carry the same class names, so each rule is matched page-wide on every style recalc (most of a thread switch's style time with many plugins). Write prefixed classes (`pinned-*`, `chat-dock-*`, `diff-plus-*`) in `src/styles.css`, imported from `app.tsx`; check `dist/app.css` for `:where([data-bb-plugin=` after a build.

## Plugins

- `bb-plugin-pinned-turns` — pins the message you are reading under and the latest reply to the top of the timeline. `src/model.ts` holds the pure rules (`bandAt` is tested against the simple `bandContent`); `src/timeline.ts` reads the timeline and outline through the SDK. Jumps steer by the row's live position each frame rather than one `scrollTo` (BB re-measures rows mid-scroll), and never touch the URL or history. Its options are a `choices` submenu of a thread action (`src/ThreadMenu.ts`; BB 0.48 retired the custom header-button slot, and header actions cannot hold choices), written through the backend's `set_setting` RPC. BB 0.48's scroll keeper writes an unexplained scroll back to the bottom while attached there, so each jump frame first dispatches a `wheel` event on the scroller to count as reader input.
- `bb-plugin-chat-dock` — moves BB's live composer shell (`[data-app-composer]`) into the right panel with `moveInto` (`src/dom.ts`), which leaves a marker and puts it back, so the draft survives. One page-wide MutationObserver docks it before a paint. The composer button only toggles `enabled` (a document capture-phase `pointerdown` guard keeps BB's composer from expanding on its click); the options are a `choices` submenu of a thread action (`src/ThreadMenu.ts`), like Pinned Turns'. Headless checks need `page.mouse.click` on the button.
- `bb-plugin-stay-at-bottom` — a content script that writes a scroller back to its bottom when BB's keeper slips. The repair is two frames (2px short, then exact) because BB's keeper ignores moves within 0.5px of its own write.
- `bb-plugin-diff-plus` — a folder tree overlaid into BB's own Diff tab. Its files come from the Git plugin's `files` read, called from `server.ts` (zod is bundled, not shared, so the page does not take it). Clicks go through BB's filter input, with glob characters escaped (`src/folders.ts`). The tree follows the tab's "Filter files" menu too: bb--git keeps those choices in a module-level Map per environment, out of reach, so `readFilters` (`src/diff-tab.ts`) takes the toolbar's `filters` prop from its React fiber, re-read when any `aria-checked` on the page changes; Viewed marks come from bb--git's `viewed` RPC. Rows the path filter shows are tinted (a closed folder holding a match, an open one whose files all match) using `src/match.ts`, which repeats bb--git's filter rules (picomatch, `dot`/`nocase`, base name without a "/", prefix fallback, "!" parts); keep it in step if BB changes them. Synced view (on by default; its "Scroll sync" and "Visible indicator lines" options are off by default) orders the tree like BB's cards, which come in the order bb--git's `files` returns them (tracked files by path, then untracked by path; `buildTree(files, compact, synced)` puts a folder where its first file is), and (`watchVisibleCards` in `src/diff-tab.ts`, `useInView` in `src/Tree.tsx`) marks rows with `data-in-view` straight on the DOM, so scrolling never re-renders the tree. Visibility comes from an IntersectionObserver rooted at the list scroller; a MutationObserver on the cards' box (children only) hands it new cards, and one-level watches on the list box, its children and the scroller re-attach when BB replaces them. An open folder's row between marked rows is marked too, so the line is unbroken; bars slide (Web Animations on `::before`) in the direction the line moved, leaving ones fading. When the marked rows leave the tree's own scroll view it scrolls just enough to show them, except within 1.5s of the reader's own input on the tree. While off it attaches nothing. Recent commits (`src/Picker.tsx`): BB's scope picker lists only commits since the merge base and drops a picked commit outside them, and the SDK cannot open another plugin's tab with a target, so the plugin orders BB's menu items with CSS `order`, portals its own commit rows into the menu, and on a click moves the merge base back N commits (`show_recent`), waits for BB to list the commit and clicks BB's own item; any non-commit scope calls `restore_base`. The merge base is BB metadata per checkout, not git (every thread on the checkout, the Diff tab's All/Committed views and `bb git status` see it; the composer's context row shows only uncommitted changes), so every exit puts it back: an abandoned pick, any other scope, the plugin's dispose and its startup (`restoreAll` over the `recent:<env>` records); calls are serialised per environment and each move and restore is logged at info with its reason. "Changes" is sticky, and so is each open folder's own row (`diff-plus-sticky`, `top` by depth, opaque, inside its wrapper, which ends it), so the open folders above the view stack under it like VS Code's sticky scroll with no script on the scroll path (a scripted version lagged the compositor's scroll). `useStuckRows` (`src/Tree.tsx`) only places the one shadow and caps the levels (`room`, 40% of the view): the shadow hangs off `.diff-plus-shade`, a zero-height element stuck at the tree's top that never un-sticks, moved down by `--diff-plus-covered` to the lowest stuck row (a shadow on the sticky rows themselves left stale paint behind in Brave after a smooth scroll unstuck them). In a split workspace each pane has its own right panel (`#thread-detail-secondary-panel-<pane id>`, which moves to the focused pane) in the same grid as every pane's timeline, so `paneThread` (`src/diff-tab.ts`) reads the thread from the timeline of the pane named in the panel's id, not the grid's first row, and `watchDiffTabs` watches those panels too. `TreeColumn` renders the tree element and the "Changes" row in every state (loading, error, empty, ready) with only what is under it changing, a spinner while the files load or the open folders are not chosen yet. Open at first defaults to All. Don't add buttons over BB's diffs: BB already has "Add to chat" on selected lines. Never pad the top of BB's list scroller (a sticky card header leaves a strip). On/off and width live in localStorage, not settings, since a setting write remounts the right panel. Icons are generated by `scripts/icons.mjs` from vscode-icons; don't round path numbers.
- `bb-plugin-lexicon` — colours a project's key terms in replies and prompts with the CSS Custom Highlight API, so nothing is added to BB's DOM, and writes nothing to the workspace. Terms are the project's own (plugin kv `terms:<projectId>`, `bb lexicon import/export`), the built-in outcomes and actions (`src/defaults.ts`) and names learned in the backend from tracked source (`src/symbols.ts`: package names and exported compound identifiers by a declaration regex, since BB has no language server and the TypeScript compiler is too big for the bundle; single words are left out). Each pane has its own lexicon: a row's thread is the prefix of its `data-timeline-row-id`, `src/paint.ts` keeps one matcher per thread (a thread with none is left plain) and reports the threads on the page to `src/Loader.tsx`, which resolves each thread's environment and polls it; nothing is shared between environments. `server.ts` serves them with a revision and the page polls every 4s (`unchanged` when nothing moved); `src/lexicon.ts` is the pure core (parse, lint, hue by parent, matcher: single tokens looked up in a Map, other phrases one regex) shared by server, page and tests, `src/paint.ts` the content script. One highlight per (shape, hue, alias) look, rule made on first use in an adopted stylesheet with `light-dark()` colours. No style draws a line (links do). Only mounted rows of `[data-timeline-items]` are painted (ids with `:assistant:` or `:user`), dirty ones repainted at most every 100ms; the composer and everything outside the timeline are never observed. It has no CSS file: `bb plugin build` turns any utility word standing alone anywhere in the folder (`fixed`, `sticky`, `underline`, `running`, `shadow`, even in a comment, test or example) into a page-wide rule, so those words are split or avoided; check `dist/app.css` for `:where([data-bb-plugin=` after a build. Agents maintain it: `src/store.ts` is the pure store (a per-project `Store` {terms, pending, log, rev} in kv `store:<projectId>`, migrated from the older `terms:<projectId>` text; `applyOp` checks an agent's add/alias/rename/retire strictly — one owner per wording, a note, no plain single words, user-pinned terms untouchable, a per-thread cap — then applies it as an `auto` term (painted lighter) or queues it when the `proposals` setting is on; renamed wordings stay as `retired` and paint as stale; `sweep` flags terms whose identifiers left the source or unseen for 30 days and retires them 14 days later; every change is logged and `undo` reverses the newest), `src/mine.ts` counts recurring names for the `mine` tool. `server.ts` registers the `lexicon` and `mine` tools (the protocol is the lexicon tool's `instructions`) and `bb.agents.configure` gives sessions a digest of the project's terms (quoted, escaped as data, ≤4096 chars). Typing `~` in the composer lists the project's own terms (`bb.ui.registerMentionProvider` in `server.ts`, best match first by `suggest`); the pill a pick inserts carries hidden context for the agent (`briefing`: wording, kind, meaning, aliases, code, quoted as data), and its item id is `<projectId>.<termId>` because `resolve` gets only the id. Concepts are stored as proper nouns in Title Case (`houseForm` in `src/lexicon.ts`, applied by `applyOp`; identifiers, actions and outcomes are left as written), a feature is one colour whatever its parent (a child inherits a hue only from a parent of the same kind) and an `option` kind has its own. `src/Settings.tsx` is the settings section (approve/reject proposals, pin/keep/remove agent terms, undo). Its switches (on, learn names, agents, proposals) are a `choices` submenu of a thread action (`src/ThreadMenu.ts`, like Chat Dock's) written through the backend's `set_setting` RPC; add later options to `SETTING_KEYS` in `server.ts`, `DEFAULTS` in `src/options.ts` and `OPTIONS` in the menu. `localStorage["lexicon:debug"]` turns on `window.__lexiconStats`.
- `bb-plugin-guest-view` — shares one thread with someone who has no BB account. **Share with guest** (a thread action, `src/ThreadMenu.ts`, in the settings group at order 103, after the other plugins' entries; its icon is the plugin's own `ShareIcon` (two people over a chain link, the link cut away around them, paths baked on the 24 grid, no `transform` attribute because the build reads that word as a utility): thread actions take only icon names, so `app.tsx` registers it with `app.experimental_icons.register` as `guest-view/share`, and the manifest's `bb.branding.icon` is the same drawing as `icons/guest-view.svg`) starts a Node HTTP server on 127.0.0.1 and a random port (`src/http.ts`) and a Cloudflare quick tunnel to it (`src/tunnel.ts`, `cloudflared tunnel --url`); BB Connect was ruled out because its links need the owner's getbb.app session. The server has three routes under `/<token>` (page, `poll`, `prompts`); anything else, a wrong token or an ended share is the same 404. The token is 32 random bytes compared in constant time; a share ends on Stop sharing, expiry (`expiryHours`, default 4), archive/delete, tunnel exit or dispose, and share state is in memory (kv `state` holds only the cloudflared pid and the shared thread ids, so the next load can say the link ended and `stopLeftoverTunnel` stops a cloudflared a dead run left, only when `/proc/<pid>/cmdline` or `ps` shows a quick tunnel of ours). Quick tunnels hold back server-sent events until the stream closes (Cloudflare documents SSE as unsupported there), so the page long-polls `poll?since=<rev>`: `src/feed.ts` stamps each item, the header and prompt outcomes with the revision they changed at and returns only what is newer, waiting up to 25s. `src/model.ts` is the pure core (tested): `guestTranscript` keeps user/assistant text, collapses work rows into counts ("Ran 3 commands, edited 2 files"), drops reasoning and turns other initiators into a note; `maskSecrets` (best effort); a small Markdown parser whose tree `src/page.ts`'s inline script builds with `textContent` under a nonce CSP. Guest prompts wait in the Owner Card's Prompt Approval (`src/Card.tsx`): Use (`useComposer().insert` of the bare text, no prefix, then the `use_prompt` RPC), Copy (clipboard only, no state change) and Dismiss. Nothing a guest writes is ever sent to the agent by the plugin (no `threads.send`), and guests are never told what the owner did: every prompt shows the same grey tick (`.gv-tick`, titled "Sent") on their page. The SDK cannot create a BB interaction for a plugin. cloudflared is never installed unasked: the card shows the command, and on Linux **Install it for me** downloads one pinned release (`CLOUDFLARED_VERSION` in `src/install.ts`, with the SHA-256 of each Linux asset from Cloudflare's release notes) into `~/.local/bin` and writes nothing unless size and hash match; bump version and hashes together, and the card's manual command checks the same hash. The page's CSS and script live in `src/page.ts` as strings, so the plugin build's utility-word rule applies to them too. The page copies BB's own thread look (BB's colour tokens, a 728px column, a composer whose row under the input holds the model and effort, then "You are <name>" with a rename icon, and BB's return-arrow send button at the right (no context ring, no hint row: the approval note is the placeholder; a line under the composer shows only problems and the end), no top bar, an always-"Working..." line with a light glint, Enter sends); the textarea is one line while idle (`.gv-peek`, over it in the same grid cell, shows the draft or the hint on one line with an ellipsis, since a textarea cannot) and two lines at least while focus is inside the form (`focusin`/`focusout` with a 120ms delay, so the send button and pencil keep it open), growing with its text; the height is a CSS transition, so `fit` measures at `auto`, puts the old height back, reads `offsetHeight` and then sets the new one; it only scrolls at 40vh. The "N sent" button has `z-index: 1` (a flex item, so no positioning word) to stay above `.gv-solid`'s soft top edge. Guest text is plain text: `plainText` in `src/model.ts` keeps printable ASCII and line breaks only (`<`, `>` and code characters stay; emoji, accents, other alphabets, zero-width, direction-control and "tag" characters go, since they can smuggle in instructions), for prompts and names; a prompt with nothing left is refused with a reason and the page notes when text was adjusted. The Owner Card (green pulsing `ShareIcon`, "N guests", one timer "<elapsed> of <length>" from `elapsedLabel` and `leftLabel(expiresAt, createdAt)`, in monospace, and a yellow pulsing "N pending" last) is one row in the git row's box (36px, 8px radius, `--surface-raised-solid`) with icon buttons (copy link, settings, stop) and a Config overlay (`src/Config.tsx`, portalled to the body): connected guests by client id and name (the poll carries `name`) with Kick (`kick` RPC; the id is refused afterwards), the link's expiry for this link (`configure`, restarts the timer), and "New guests see previous history" (`showHistory`; when off a guest's first poll records the item ids that exist and `hideHistory` in `src/feed.ts` filters them out of its payloads, prompts included), "Guests know about other guests" (`showGuests`, on by default: off sends `setGuests(null)`, so the page shows the icon with no count, and keeps `setPrompts` empty so a guest sees only their own), "Show guests the model" (`showModel`, off by default: `refresh` blanks `model` and `effort` in the header before the feed sees it) and "Guests see each other's prompts" (`showPrompts`, off by default, ignored while `showGuests` is off: `setPrompts` then carries `{id, name, text}` (text masked) for everyone, and an empty list while off, so a page falls back to its own prompts). The Owner Card is closed until clicked and always opens ("No messages received yet" when empty; the click target is everything left of the link icon, `.guest-view-toggle`; the hover chevron is always there), so a new prompt only raises the pending count; used and dismissed prompts go to a collapsed History, the first thing in the opened part, oldest first with the newest at the bottom (`OwnerState.history` from the server's prompts with `resolvedAt`, `HistoryList`/`HistoryRow` in `src/Card.tsx`, a Copy button on each, opened by hand only, `max-height: 200px`; Dismiss and Copy are icon-only); Prompt Approval scrolls (`max-height: min(40vh, 320px)`), cuts each prompt at four lines and measures the cut with a `ResizeObserver` (chevron only when `scrollHeight > clientHeight`), and puts Use, Copy and Dismiss in a right-hand column. Use is a split button (`src/SplitButton.tsx`): the button inserts the bare text, its chevron opens a menu portalled to the body (placed from the chevron's box, closed by Esc, an outside click, a scroll or the window changing size) with **Use with the name**, which inserts `attributed(name, text)` from `src/model.ts` (`Lydia says: <text>`, the name on its own line above a multi-line prompt); the owner picks the form each time, so there is no setting and Copy stays plain. On the guest page the Presence Row is not a row any more: the same green pulsing mark (`markSvg` in `src/mark.ts`, which `ShareIcon` also draws from, so there is one drawing) and the `Feed.setGuests` count ("N guests") sit in the Guest Composer's toolbar left of the send button (the Live Tag is gone: the icon says it), the whole document scrolls (`document.scrollingElement`; the composer's `.gv-bar` sticks to the bottom but has no background: only `.gv-solid` (the composer and the Notice Line) covers the text, so a reader scrolled up sees the text beside the "N sent" button, a `ResizeObserver` on it keeps a reader who was at the end there, `interactive-widget=resizes-content` in the viewport meta; the sticky word is split in `src/page.ts`) and all sizes are 20% larger than BB's 13px base (the model chip hides below 600px, "You are" below 440px). The Prompts Row (no title: just "N sent", as wide as its content and right-aligned while closed, full width open; `toggleOpen` in `src/page.ts` animates the box between the two measured sizes with the Web Animations API, anchored at the right, the list keeping its final width and cut off, and on closing it stays on screen until the box has shrunk) sits above the composer (`renderMine` in `src/page.ts`: "N sent", a scrolling list that opens at its end, two-line cut with a chevron only when cut, `<name>: <text>` and the tick for everyone when shared). Icons are drawn in `src/Icons.tsx`. `expiryHours` defaults to 4. Limits and hardening (from the Fable review; FINDINGS.md of the owning thread lists the decisions): `src/waiters.ts` `WaitSet` caps waiting polls per page (3), per address (6) and per share (40), since a quick tunnel carries 200 requests for everyone (an over-cap poll releases the oldest as "nothing new"; a full share answers a retryable 429); a share lets 5 pages per address watch and remembers 500; `submit` needs a `clientId` the share has seen poll (24 hex), so a removal cannot be dodged by leaving it out; the page never ends on network errors or 429 (backoff up to 30s, a "Try now" button, `nudge` on `online`/visibility) and only a 404 or an `ended` field ends it; a first poll before the thread has been read answers `rev: 0` without fixing the guest's starting point (`showHistory` off would otherwise show them everything); `readThread` takes a `ParseMemo` so only changed messages are parsed, cuts a message at `MAX_MESSAGE_CHARS`, and asks for the model only when `showModel`; `maskSecrets`, `parseInline` and the heading and quote rules are linear (tests give each a time budget; quote depth is capped at 6 because a deep run overflowed the stack and stopped every guest's feed); `cleanName` drops colons and "says" and refuses reserved role names (also with look-alike digits); `NoticeBatch` (`src/notify.ts`) sends the first push at once and a summary every 30s; the `share` RPC takes `via: "app"` from the menu and the card, and any other caller gets a log warning and a push, because the SDK's RPC caller is only `plugin` or `client`, so the CLI cannot be told from the app (a tripwire, not a lock, and spoofable); `redactTunnelLine` cuts the token and query out of every cloudflared line before it is logged; `Tunnel.stop()` sends SIGTERM and SIGKILL after 3s and `stopServerIfUnused` awaits it. Tests: `src/server.test.ts` runs the real `server.ts` and guest server with a fake `bb` and a shell script as cloudflared (share lock, waiting caps, removal, push batching, reload record, leftover process); keep bare utility words (`running`, `visible`, `block`, `inline`) out of tests and comments too.

## BB page facts (bb-app 0.47, undocumented, can change)

- Timeline scroller `[data-page-scroll-viewport]`; rows `[data-timeline-row-id]` in DOM order, ids equal the timeline data's row ids. Virtualized at ≥ 20 top-level rows (`[data-timeline-window-spacer]` placeholders); the last row is always mounted.
- Right panel `#thread-detail-secondary-panel` (`data-panel-size` 0 when hidden); on phone width it is `[data-testid=secondary-panel-shelf]`. Every plugin setting write remounts its content.
- `experimental_Icon` names are BB's own set, not lucide; a missing name renders the fallback.
