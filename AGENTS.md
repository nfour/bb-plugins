# BBPlugins

A pnpm workspace of BB plugins. One folder per plugin, `bb-plugin-<id>/`, each a normal BB plugin package (`package.json` carries the `bb` manifest). Use the `bb-plugin-authoring` skill for the Plugin SDK contract.

## Code here, run it from bb

Write all plugin code in this repo. Never edit a plugin inside `~/.bb/plugins/` — that directory holds BB's runtime state, not source. Link a plugin by path so bb loads this checkout in place:

```sh
bb plugin install ./bb-plugin-<id> --yes   # once per plugin
bb plugin dev ./bb-plugin-<id>             # rebuild + reload on every save
```

## Workspace

- Install with `pnpm install` at the root, never `npm install` in a plugin.
- `pnpm check` typechecks every plugin; `pnpm build` runs `bb plugin build` in each; `pnpm --filter <pkg> test` runs a plugin's `node --test` checks (pinned-turns, diff-plus, lexicon, performance, guest-view, minimap).
- `bb plugin types ./bb-plugin-<id>` repins the SDK when bb upgrades.
- Releases are tags `<id>/vX.Y.Z`; `.bb/plugins.json` indexes the plugins for git installs. Each release bumps `package.json`'s version and adds an entry at the top of the plugin's `CHANGELOG.md` (what a user notices, not the code), in the same commit as the change.
- Styling: no Tailwind utility classes. `bb plugin build` scopes every utility it finds anywhere in the folder (code, comments, README) as `:where([data-bb-plugin="<id>"], …) .flex`, and BB's own elements carry the same class names, so each rule is matched page-wide on every style recalc (most of a thread switch's style time with many plugins). Write prefixed classes (`pinned-*`, `chat-dock-*`, `diff-plus-*`) in `src/styles.css`, imported from `app.tsx`; check `dist/app.css` for `:where([data-bb-plugin=` after a build.

## Plugins

- `bb-plugin-pinned-turns` — pins the message you are reading under and the latest reply to the top of each pane's timeline. `src/model.ts` holds the pure rules, `src/watch.ts` the delta-reading timeline watcher (tested with `mock.timers`), `src/PinnedTurns.tsx` the bar. Options are a `choices` submenu of a thread action written through `set_setting`/`set_halves`. No utility words anywhere in the folder; check `dist/app.css` for `:where([data-bb-plugin=` after a build. Details: `bb-plugin-pinned-turns/NOTES.md`.
- `bb-plugin-chat-dock` — moves BB's composer shell (`[data-app-composer]`) into the right panel with `dockInto`/`moveInto` (`src/dom.ts`): a strip (`Strip.tsx`) or a Chat tab (`Dock.tsx`); the phone drawer, outside React's root, gets an overlay in `#root` (`src/overlay.ts`). In a split workspace the panel is `#thread-detail-secondary-panel-<pane id>` and the focused pane's composer docks. One structural MutationObserver plus a 2s backstop that sleeps in a background tab; palette commands in `src/Commands.tsx`. Test the Chat tab by rewriting the settings GET, never the user's `locked`. Details: `bb-plugin-chat-dock/NOTES.md`.
- `bb-plugin-performance` — a nav-panel tab (`app.slots.navPanel`, route `/plugins/performance/performance`) that measures how far BB is from feeling native in the user's real sessions, and which plugin is behind a slowdown. Not released yet. The page side is `src/collector.ts`, a content-script singleton that attaches only while `enabled`: PerformanceObservers for `long-animation-frame` (scripts attributed to a plugin by `sourceURL`, matched to each plugin's bundle URL from `GET /api/v1/plugins`; anything else is BB core) and `event` (typing and click latency), a rAF frame sampler that runs only within 400ms of a key, wheel, scroll or pointerdown, the Navigation API `navigate` event plus a MutationObserver that settles after 100ms of quiet (capped 2s) for thread switches and page changes, an attribute observer on `data-panel-size` for panel opens, a 30s timer for heap samples, and a count of each plugin's page-wide `) .word` rules from `document.styleSheets`. Frames in the first 10s of a fresh load are start-up, never idle. Windows are histograms (`EDGES` in `src/model.ts`), flushed once a minute and on `pagehide` through the backend's `ingest` RPC, one flush at a time. `src/model.ts` is the pure core (targets, histograms, `measures`, `pluginRows`, `ownerOf`, `driverAt`, `heapSlope`), tested with `src/jsonl.ts` and `src/proc.ts`. `server.ts` appends lines to `~/.bb/plugins/performance/metrics/YYYY-MM-DD.jsonl` (14 days, 5MB per file; no ids, titles or text are written, routes have ids stripped), keeps the last 400 lines for the dashboard's `snapshot` RPC, serves `recent_threads` (ids only, for the benchmark), and samples the server once a minute (event loop delay, CPU, RSS, `bb.host` workers from `/proc`, handler call deltas per plugin from the page-reported `handlerStats`); `bb performance summary|files` reads the file. Plugin back-ends run inside BB's server process (the log's `pid` equals the server's), so only `bb.host` workers have their own CPU and memory; `handlerStats.maxMs` is lifetime wall time including awaits, so it is written but never shown. React renders of a plugin count as BB core in Long Animation Frames. The charts are plain SVG in `src/charts.tsx` (no library; `series` and `shares` in `src/model.ts` bucket the window lines): bars, trends and the plot area stretch with `preserveAspectRatio="none"` and non-scaling strokes, but any dot is an HTML box over the SVG (`.perf-pt`), because stretched circles turn oval. Each LoAF entry is also split by `splitOf` (script, forced layout, style and layout from `styleAndLayoutStart`, other) into `window.split`, per-owner `forced` and `by` call kind (`kindOf` of `invokerType`/`invoker`), and `slow.split`; entries before `loafSeen`/`eventSeen` are skipped, because an observer attached again replays the browser's buffer (the Loader keeps the RPC in a ref so the effect only reruns on a real setting change). Actions live in the collector: `probe()` (per plugin sheet, `sheet.disabled` toggled and one `getComputedStyle(document.body).color` read, which recalculates style but does not lay out; one plugin per task, median of three, its frames ignored through `ignore` ranges that open at the start), `bench()` (thread switches through `useBbNavigate().toThread`, resolved by the `nav` listener, first hop dropped, 5s cap, returns to the tab), `mark()` (from `recentFrames`, last 15s), `pause()`; `bench` with `cssOff` switches every plugin sheet but its own off (`offSheets`, always restored in `finally` and on detach) for the Compare plugin CSS action, kept as `benchOff`; results persist in localStorage `performance:last`. Plugin bundle sizes come from the plugin list's `jsBytes` (the browser's resource timing buffer fills at 250 entries). `src/report.ts` builds the markdown report from what the dashboard shows. The plugin rows are an accordion (`PluginDetail` in `src/Panel.tsx`); a probe time includes restyling the plugin's own elements on screen, so the elements are shown beside it. Forced layout is recorded per call site in `window.sites` (`owner · file (BB core only) function@position`, top 12 per window by `topSites`); in BB's bundle the top sites are React's scheduler (`E` in boot-vendor) and its discrete-event dispatch, so the cost is React render and layout effects, not one function. A slow input's `phases` (`phasesOf` of Event Timing: wait, handlers, paint) and the owners of frames that overlapped it are written 300 ms after it, once the frames have been reported. Class words behind page-wide rules come from `classOfSelector`/`classParts` (escapes undone; variants stored as `name:`). Test strings must not hold real utility words either (`zed` stands in). Slow frames that two pages sharing a process both report (same ms, within 50ms) are listed once. The nav icon's badge (`experimental_useBadge`) is the worst gap as a multiple of its target, from what this page has already sent. Options (`enabled`, `writeFile`, `sampleServer`) are a `choices` submenu of a thread action (`src/ThreadMenu.ts`) written through `set_setting`. The panel gets no scroller from BB, so `.perf-scroll` (`height: 100%`, `overflow-y: auto`) is its own; headless wheel events do not scroll, use PageDown. Use BB's own icon names (`TimeSchedule`, `ArrowReloadHorizontal`): an unknown name renders a fallback bolt. Utility words are avoided in the whole folder (the table element and the page's hidden property are built from two strings in `src/Panel.tsx` and `src/page.ts`); check `dist/app.css` for `:where([data-bb-plugin=` after a build. A headless browser draws on the CPU, so its frame numbers are far worse than a real screen's; `bb browser-automation` screenshots must be JPEG (a PNG request stops the session).
- `bb-plugin-minimap` — a strip over each thread pane's right gutter that stands in for the scrollbar: one rectangle per row (canvas, slider div, hover note), laid out in its own pixels from the thread's timeline data because BB virtualises rows. One strip per pane (`paneThreads` reads threads off the page). Click/wheel glides are its own and write `scrollTop` after a synthetic `wheel` for BB's keeper. Never put a bare Tailwind word anywhere in the folder; check `dist/app.css` for `:where([data-bb-plugin=`. Details: `bb-plugin-minimap/NOTES.md`.
- `bb-plugin-diff-plus` — a folder tree overlaid into BB's own Diff tab (no BB slot: it finds the tab by markup). Files come from bb--git's `files`/`viewed` via `server.ts`; clicks go through BB's search box; recent commits move the checkout's shared merge base and every exit puts it back. In a split workspace the tab reads its own pane's thread. No utility words anywhere in the folder (dist/app.css must have 0 `:where([data-bb-plugin=` rules). Details: `bb-plugin-diff-plus/NOTES.md`.
- `bb-plugin-lexicon` — colours a project's key terms in replies and prompts with the CSS Custom Highlight API, so nothing is added to BB's DOM, and writes nothing to the workspace. Terms are the project's own (plugin kv `terms:<projectId>`, `bb lexicon import/export`), the built-in outcomes and actions (`src/defaults.ts`) and names learned in the backend from tracked source (`src/symbols.ts`: package names and exported compound identifiers by a declaration regex, since BB has no language server and the TypeScript compiler is too big for the bundle; single words are left out). Each pane has its own lexicon: a row's thread is the prefix of its `data-timeline-row-id`, `src/paint.ts` keeps one matcher per thread (a thread with none is left plain) and reports the threads on the page to `src/Loader.tsx`, which resolves each thread's environment and polls it; nothing is shared between environments. `server.ts` serves them with a revision and the page polls every 4s (`unchanged` when nothing moved); `src/lexicon.ts` is the pure core (parse, lint, hue by parent, matcher: single tokens looked up in a Map, other phrases one regex) shared by server, page and tests, `src/paint.ts` the content script. One highlight per (shape, hue, alias) look, rule made on first use in an adopted stylesheet with `light-dark()` colours. No style draws a line (links do). Only mounted rows of `[data-timeline-items]` are painted (ids with `:assistant:` or `:user`), dirty ones repainted at most every 100ms; the composer and everything outside the timeline are never observed. It has no CSS file: `bb plugin build` turns any utility word standing alone anywhere in the folder (`fixed`, `sticky`, `underline`, `running`, `shadow`, even in a comment, test or example) into a page-wide rule, so those words are split or avoided; check `dist/app.css` for `:where([data-bb-plugin=` after a build. Agents maintain it: `src/store.ts` is the pure store (a per-project `Store` {terms, pending, log, rev} in kv `store:<projectId>`, migrated from the older `terms:<projectId>` text; `applyOp` checks an agent's add/alias/rename/retire strictly — one owner per wording, a note, no plain single words, user-pinned terms untouchable, a per-thread cap — then applies it as an `auto` term (painted lighter) or queues it when the `proposals` setting is on; renamed wordings stay as `retired` and paint as stale; `sweep` flags terms whose identifiers left the source or unseen for 30 days and retires them 14 days later; every change is logged and `undo` reverses the newest), `src/mine.ts` counts recurring names for the `mine` tool. `server.ts` registers the `lexicon` and `mine` tools (the protocol is the lexicon tool's `instructions`) and `bb.agents.configure` gives sessions a digest of the project's terms (quoted, escaped as data, ≤4096 chars). Typing `~` in the composer lists the project's own terms (`bb.ui.registerMentionProvider` in `server.ts`, best match first by `suggest`); the pill a pick inserts carries hidden context for the agent (`briefing`: wording, kind, meaning, aliases, code, quoted as data), and its item id is `<projectId>.<termId>` because `resolve` gets only the id. Concepts are stored as proper nouns in Title Case (`houseForm` in `src/lexicon.ts`, applied by `applyOp`; identifiers, actions and outcomes are left as written), a feature is one colour whatever its parent (a child inherits a hue only from a parent of the same kind) and an `option` kind has its own. `src/Settings.tsx` is the terms page, shown both as the settings section and as a nav panel (`navPanel` "Lexicon", path `terms`, which scrolls itself because BB gives a nav panel no scroller): the four switches on one line, then a data sheet with a row for the global rules (the built-in `DEFAULT_TERMS`, read-only) and one per project, with counts from the `overview` RPC (read once, and again after an edit, never polled). A row opens like an accordion (the current project's starts open) into a 400px scrolling list of that scope's terms grouped by kind, every kind listed even when empty (a sticky header each, with "+ Add term" for a project: the `add_term` RPC, `userAdd` in `src/store.ts`, which pins it, accepts a plain word and needs no note, but still refuses a wording another term or a built-in owns). Each term has Disable/Enable: `disabled` keeps the entry and its wordings owned (so nothing else can claim them) but `compile`, `suggest`, `digest` and `sweep` skip it and agents may not alias, rename or retire it; a built-in word is switched off for every project through the `set_default` RPC (kv `defaults-off`, folded into the revision, `overview` returns the list). Disabled rows are dimmed, sort last and leave the kind's count chip. A term is two lines (name, aliases, actions; meaning under). Stale terms come first, then agent, then yours; waiting proposals sit on top with Approve/Reject; Pin/Keep/Remove; Undo last change. Rows stay open independently, read with `review` only while open, rows `content-visibility: auto`. The sheet and its roles are built from two strings (`TABLE` in the file), since the word alone becomes a page-wide rule. Its switches (on, learn names, agents, proposals) are a `choices` submenu of a thread action (`src/ThreadMenu.ts`, like Chat Dock's) written through the backend's `set_setting` RPC; add later options to `SETTING_KEYS` in `server.ts`, `DEFAULTS` in `src/options.ts` and `OPTIONS` in the menu. `localStorage["lexicon:debug"]` turns on `window.__lexiconStats`.
- `bb-plugin-guest-view` — shares one thread with someone who has no BB account: a thread action starts a local HTTP server and a Cloudflare quick tunnel; the guest page long-polls (quick tunnels hold SSE back) and suggests prompts that wait on an Owner Card above the composer (Use puts text in the composer; nothing a guest writes reaches the agent by itself). The thread is read as deltas (`src/delta.ts`). The guest page's CSS and script are strings in `src/page.ts`, so the build's utility-word rule applies to them too. Details: `bb-plugin-guest-view/NOTES.md`.

## BB page facts (bb-app 0.47, undocumented, can change)

- Timeline scroller `[data-page-scroll-viewport]`; rows `[data-timeline-row-id]` in DOM order, ids equal the timeline data's row ids. Virtualized at ≥ 20 top-level rows (`[data-timeline-window-spacer]` placeholders); the last row is always mounted.
- Right panel `#thread-detail-secondary-panel` (`data-panel-size` 0 when hidden); on phone width it is `[data-testid=secondary-panel-shelf]`. Every plugin setting write remounts its content.
- The phone drawer (bb-app 0.49) is portaled to `body`, outside `#root`, as `role=dialog aria-modal`: React ignores events on BB elements moved into it. Open it is full width and pinned right (opening animates its width, 296→390px at 390px; it never slides; a swipe moves the page under it), z-index 45 (0 closed, with `inert`); BB's scale puts toasts at 49 and menus at 50. It closes on a thread switch.
- BB's keyboard handler sets `--bb-shell-height` (visual viewport height) and `--bb-safe-area-bottom: 0px` on `body`; the drawer's height is that variable.
- The composer footer `[data-follow-up-composer-footer]` fades out under BB's unlayered container style query on `--follow-up-composer-container-compact` (composer ≤ 30rem wide, or thread pane ≤ 26rem tall; the side panel is not inside the pane's container) until the composer is expanded; collapsed on a phone it is not rendered at all. Plugin CSS is loaded unlayered.
- `experimental_Icon` names are BB's own set, not lucide; a missing name renders the fallback.
